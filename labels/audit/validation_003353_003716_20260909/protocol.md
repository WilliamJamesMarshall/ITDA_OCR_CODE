# 검증 프로토콜

## 범위와 원본 보호

- 003353.jpg–003716.jpg, 364장 전수 검증.
- 사용자가 수정한 manual.xlsx의 `검수 정답지!C2:C365`를 정답으로 고정한다.
- 원본 CSV, XLSX, inspect.ndjson은 읽기만 하며 SHA-256을 전후 대조한다.
- 운영 src와 가중치는 수정하지 않는다. 실험용 함수 교체는 별도 Python 프로세스 메모리 안에서만 적용한다.
- 판독 프로세스는 JPEG만 읽는다. 정답, metadata, 이전 판독 결과, 이미지 ID별 정답 규칙을 추론에 쓰지 않는다.
- 정답은 후처리 실험 코드와 테스트를 정한 뒤 별도 채점 프로세스에서만 비교한다. 이 364장은 이미 오류 유형을 알고 있는 개발 검증셋이며 독립 블라인드 테스트셋이 아니다.

## 실행 순서

1. baseline: 현재 운영 pipeline.py/date_extraction.py와 기본 설정 그대로 이미지부터 전수 실행한다.
2. p1_replay: baseline에서 저장한 모든 OCR 출력에 과거 연도 범위(2000–2099)와 부분 날짜 출력을 적용한다.
3. p2_replay: p1에 명시적 MDY/DMY, 일 값이 12를 초과하는 두 자리 연도 MDY, YYYY MON DD를 추가한다. 단서가 없는 두 자리 연도 3요소의 모호함은 기존 YMD 해석을 유지한다.
4. p3_replay: p2에 source/variant 좌표계별 병합·문맥 분리, 가까운 키워드만 결합, 근거 없는 550일 이내 최후 날짜 우선 규칙 제거를 적용한다. 좌표를 원본으로 환산하는 방식은 이번에 구현하지 않고 다른 좌표계 사이 연산을 차단한다.
5. p3: 같은 개선안을 새 프로세스에서 이미지부터 다시 전수 실행한다. 실제 조기 종료와 조건부 복구 경로를 포함해 정확도와 처리시간을 측정한다.

재평가는 모든 baseline OCR 패스를 고정한 후처리 비교다. 새 후처리로 조기 종료하거나 추가 패스를 요청하는 온라인 실행과 다르다. 재평가 처리시간을 전체 OCR 처리시간으로 표시하지 않는다. CPU OCR 작업은 동시에 실행하지 않는다.

## 지표

- 주 지표: 386개 `추출한 날짜`와 `정답 날짜` 문자열의 완전일치율. 부분 날짜의 NONE 위치까지 일치해야 정답이다.
- 완전 날짜 354건, 부분 날짜 25건, NONE 7건을 별도 집계한다.
- 런타임 예외는 NONE 정답과 우연히 일치해도 실패로 집계하고 결과 표에는 ERROR를 기록한다.
- 실측: 모델 초기화 시간, 초기화 포함 측정 구간 전체 시간, 이미지별 처리시간 합계·중앙값·95백분위, OCR 패스 수.
- 반복 측정은 하지 않는다. 개발 PC의 1회 실행이며 공식 평가 환경 성능으로 해석하지 않는다. 500장 시간은 선형 환산치일 뿐 실측이 아니다.
- 이미 알고 있는 표본을 이용하므로 독립 일반화 성능으로 주장하지 않는다. 정답 확인 후 실험 규칙을 재조정하지 않는다.

## 출력

- labels 폴더: baseline 및 p3 결과 XLSX, 각 단계의 같은 8열 CSV, 종합 보고서.
- XLSX는 원본의 시트명·열·정답·비교 수식을 유지한 새 파일이며 원본에 덮어쓰지 않는다.
- audit 하위 폴더: 실행 코드, 이미지/원본 해시, 원시 OCR 로그, 환경 및 시간 기록, 테스트와 채점 근거.

## 해석 한계

앞선 384/386 판독은 주석 정보와 이미지 검토를 사용했던 작업이다. 이번 이미지 단독 CPU OCR과 입력 조건이 다르므로 직접 동일시하지 않는다. 이번에는 메타데이터 기반 주석 읽기 방식의 성능을 다시 계산하거나 재현하지 않는다.

데이터에 맞춘 모델 학습, 외부 VLM API, 새 검출 모델 도입, 운영 코드 반영은 이번 검증에 포함하지 않는다.
