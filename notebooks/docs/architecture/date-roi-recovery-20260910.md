# 날짜 영역 복구 우선순위 후속 작업

2026-09-10. 숫자 미검출·오독을 줄이기 위한 복구 대상 선택을 구현하고 검증한다. 파일별로 작업을 나누지 않고 선택 규칙·회귀 테스트·실제 OCR 비교를 하나의 기능 묶음으로 처리했다.

## 확인한 원인과 변경 범위

기존 코드는 숫자가 4개 이상이고 `. / - :` 중 하나가 있는 줄을 OCR 신뢰도순으로 최대 2개 선택했다. 실제 기록과 원본을 확인했을 때 선명한 전화번호·영양성분이 흐린 날짜를 밀어내는 사례가 있었다. 예를 들어 이전 번호 `003654`(현재 `003645`)는 날짜 영역이 `a0E1.0R0EH`로 읽혔으나, 기존 확대 대상은 자몽 함량과 원재료 줄이었다. 수정 후 이 날짜 영역을 다시 읽기는 하지만 숫자 오독이 남아 정답으로 복구되지는 않았다.

수정안은 같은 최대 2개 영역 안에서 다음 순서로 선택한다.

1. 짧은 숫자 중심 줄이며 날짜 파서가 실제 날짜 후보를 만들 수 있는 영역.
2. 짧은 숫자 중심의 손상된 날짜 조각. 구분자가 있고 숫자 4개 이상, 또는 구분자가 둘 이상이고 숫자 3개 이상인 줄을 제한적으로 포함한다.
3. 기존의 기타 숫자 영역. 전화번호·영양성분·주소·로트 등은 우선순위를 낮추지만 완전히 제거하지는 않는다.

같은 우선순위 안에서는 OCR 신뢰도순이며 동점은 원래 순서를 유지한다. 숫자 비율 25% 이상, 길이 32자 이하로 날짜 조각 승격 범위를 제한한다. 숫자를 치환하거나 새 날짜를 만들어내는 규칙이 아니다. 확대 후 실제 OCR과 기존 날짜 판정기를 다시 통과해야 한다.

DMY 최종 기본값, 명시 순서 우선권, 부분 날짜의 NONE 유지, 순서만 모호할 때 추가 OCR을 하지 않는 동작은 그대로다. 모델·가중치·일련번호별 예외·제품 규칙은 추가하지 않았다. 원본 이미지와 정답 라벨도 수정하지 않았다. karpathy-guidelines에 따라 확인된 복구 선택 문제만 수정했다.

## 채택하지 않은 실험

숫자 없이 `소비기한`, `Best before` 같은 항목명만 읽힌 경우에도 주변을 확대하는 시안을 실제 27장으로 비교했다.

- 정답: 14/27 → 14/27, 개선·손실 각각 0건.
- OCR 호출: 117 → 132회.
- 이미지 처리 합계: 137.48 → 143.97초.

항목명만 있는 영역은 날짜가 실제로 다른 곳에 인쇄되어 있을 수 있다. 이 실험에서 비용 증가만 확인되어 해당 확장을 제외했다. 실험 코드와 결과는 `rejected_label_anchor_pipeline.py`, `pilot_result.json`에 보존했다. 현재 적용 코드의 성능으로 이 시안의 결과를 인용하면 안 된다.

## 검증 범위

직전 단계의 SHA-256 고정 705건을 재사용했다. 숫자 영역 선택이 바뀌고 첫 OCR에서 종료하지 않는 사례 67건을 전부 골랐으며, 대조 6건을 더해 실제 변경 전후 73장 비교 대상으로 고정했다. 이 67건은 모두 기존/변경 후 선택 영역 수가 2개로 동일했다.

같은 백엔드·CPU 4스레드·모델을 사용하고 각 이미지의 전후 실행 순서를 번갈아 적용한다. 타이머에는 이미지 로딩·OCR·날짜 판정이 포함되며 모델 초기화와 Python 시작은 제외된다. 처리 전후 이미지 해시 및 실행 전후 소스 해시를 검증한다. 변경 전 파이프라인은 작업 시작 시 고정한 사본이며 날짜 파서는 두 실행에서 동일하다.

개발에 사용한 자료이므로 독립 정확도 평가가 아니다. 이전 705건의 저장 OCR 정확도와 이 선별된 실제 실행 정확도를 직접 비교하거나, 73장 시간을 500장으로 곱해 합격이라고 판단하지 않는다.

## 실제 비교 결과

| 73장 실제 전후 비교 | 변경 전 | 적용 후 |
|---|---:|---:|
| 정답 | 56/73 | 56/73 |
| OCR 호출 | 323회 | 306회 |
| 이미지 처리 합계 | 535.73초 | 510.94초 |

출력 73건이 전부 동일하며 정답 개선 0건, 손실 0건이다. 11장은 호출이 줄고 3장은 늘었으며 59장은 같다. 합계 17회(5.26%) 절감했다. 한 번의 교차 실행에서 처리시간은 24.79초(4.63%) 줄었으나 반복 측정이나 공식 환경의 전체 처리속도 합격을 의미하지 않는다. 두 실행의 첫 원본 OCR 결과도 73/73건 동일했다.

- 자동 테스트 **93개 통과**, `git diff --check` 오류 없음.
- 입력 이미지의 전후 SHA-256과 실행 전후 코드 해시 일치.
- 날짜 파서는 작업 시작 사본과 바이트 단위로 동일하다. 기존 저장 OCR 705건에 대한 555/705를 이번 단계의 새 정확도 성과로 재집계하지 않는다.

즉, 이번 채택 결과는 **정답률 개선이 아닌, 검증한 개발 자료에서 출력 유지와 복구 호출 절감**이다. 정답률 향상이라고 보고하지 않는다.

## 다음 작업 — 있음

1. 날짜 영역을 올바르게 선택해도 남는 숫자 오독·누락을 개선한다. 특히 점 인쇄 숫자/흐린 글씨를 위한 영역 전처리와 인식 성능을 비교하되, `E`를 임의의 숫자로 바꾸거나 빠진 연도를 정답에서 채우지 않는다.
2. 제조일·소비기한 및 복수 날짜의 역할 연결, 이미지에서 확인 가능한 날짜 순서 근거를 보완한다. 일련번호 정답표를 추론 규칙으로 넣지 않고, 근거가 없으면 사용자가 정한 DMY 기본값을 유지한다.
3. 변경안은 기존 정답 손실과 호출·시간을 함께 검증한 뒤, 제품/중복 그룹을 분리한 독립 평가 및 초기화·입출력을 포함한 공식 환경의 500장 실행으로 확인한다.

내부 정확도 95%는 미달이며, 500장을 2,400초보다 충분히 빠르게 처리한다는 목표도 아직 검증되지 않았다. 2,400초는 처리 목표가 아닌 타임아웃으로 유지한다. 이번 비교의 미해결 17건은 `remaining.md`에 이전/현재 번호, 정답, 출력, 자동 원인 분류를 함께 정리했다. 전체 개발 자료의 미해결 문제를 이 17건으로 축소해서 해석하면 안 된다.
