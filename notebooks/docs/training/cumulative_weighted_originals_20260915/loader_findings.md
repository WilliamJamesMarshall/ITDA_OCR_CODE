# 실행 전 실제 crop 검사에서 발견한 로더 문제

원본·전사·상품 그룹·모델 구조는 변경하지 않았다. v1/v2는 모델 및 optimizer 진입 전 준비 실패로 보존한다.

1. 목록 파일은 CRLF이며 Paddle 원래 파서는 LF만 제거한다. CR은 원래 전사의 일부가 아닌 파일 레코드 종결자다. 새 어댑터는 승인 전사와 정확히 대조한 뒤 메모리의 레코드 구분자만 LF로 정규화한다. 원본 TXT/주석은 수정하지 않는다.
2. 원래 NRTRLabelEncode는 max_text_len=25 배열에 시작·종료 토큰을 함께 넣으므로 실제 본문 24/25자를 거부한다. 해당 optimizer crop은 42개(24자 24개, 25자 18개), 원본 40장, 회차별 3회 5개·4회 20개·5회 17개다.
3. 기존 데이터셋은 거부된 crop 대신 다음 crop을 재귀적으로 반환한다. 과거 sampler 인덱스 전수 확인은 실제 crop 전수 사용의 충분한 증거가 아니었다. 과거 점수·checkpoint·보고서는 보존하며 해당 한계를 이번 기록으로 보완한다.
4. 이번 weighted adapter는 CTC 본문 제한과 모델 max_text_length=25를 유지하고 NRTR 정답 배열만 27칸으로 설정한다. BOS/EOS 포함 공간이며, 새 문자·더 긴 원문·모델 파라미터를 추가하지 않는다. 이를 통해 계획에서 승인한 3,316개 crop을 양쪽 손실에서 모두 사용한다.
5. 대체 재귀는 오류로 차단한다. 모든 crop을 동기식으로 디코딩·라벨 인코딩한 뒤 실제 shuffled loader에서 중복·누락·가중치·잔여 batch를 다시 확인한다. optimizer는 이 검사 통과 후에만 실행한다.

이번 후보는 회차/원본 가중치뿐 아니라 NRTR crop별 손실 평균, 잔여 batch의 고정 분모, 실제 승인 crop의 누락 없는 로딩이 함께 반영된다. 성능 변화 전부를 회차 가중치 단독 효과라고 해석해서는 안 된다.
