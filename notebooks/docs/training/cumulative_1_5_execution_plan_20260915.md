만약 RAM 때문에 두 슬롯 병행이 안전하지 않으면 중복 실행하지 않고 순차 전환을 보고한다. 각 회차 목표 합산 6752초, 약 112.5분이며 준비 포함 약 125~145분으로 늘어난다. 최초 테스트의 CPU 조건과 달라진 점을 보고서에 명시한다.

원본은 학습대상데이터에서만 복사하고 고정 목록·원본 SHA를 확인한다. 1~5회 각각 새 평가 디렉터리를 사용하고 과거 최초 출력·보고서를 덮어쓰지 않는다. 이미 유효하게 끝난 이번 새 평가 회차도 재실행하지 않는다. 실패·부분 결과·시간 초과는 그대로 남긴다.

이번 필수 결과는 개선 코드+새 모델의 5회 평가다. 과거 결과와 비교하되 코드/모델이 둘 다 바뀐 경우 모델만의 효과라고 주장하지 않는다. 사용자가 모델 기여도를 더 분리해 보고 싶다면 동일 개선 코드+기존 모델의 5회 대조 평가를 별도 선택사항으로 제안한다. 추가 약 75~90분이며 기본 소요시간에는 포함하지 않는다. 자동으로 20회짜리 전수 조합 실험을 확대하지 않는다.

회차별 보고서 5개와 종합 보고서 1개를 저장소 `notebooks/docs/training/cumulative_1_5_20260915/` 아래에 정리할 예정이다. 대용량 trace·전체 상세 CSV·checkpoint는 작업 공간에 두고, 저장소에는 집계·재현 명령·코드/모델/목록/정답 SHA와 원본별 개선·퇴행 목록 등 검토 가능한 최소 결과를 넣는다. 정답/이미지 공개 범위를 자동 확대하지 않는다.

보고 항목:

- 각 회차 주 정확도/95% 여부, 연·월·일별 정답·손실, 완전 날짜 일치.
- 최초 기준과 새 정답 기준을 구분한 개선/퇴행 및 실패·누락·출력 형식.
- 초기화~종료 전체 시간·시간 목표·강제 종료, CPU·스레드·메모리.
- 코드 수정 전후와 실제 학습 pool·epoch·crop 수·제외 사유·모델 해시.

## 8. 사용자 채택 후 main 커밋·push

1. 사용자가 검토한 보고서 SHA와 채택한 release의 코드·모델 SHA를 실제 채택 지시에 묶는다. 보고서 제출 자체는 채택 승인이 아니다.
2. 기존 기본 모델을 백업하고 후보 export와 평가 모델의 SHA가 동일한지 확인한다.
3. 저장소의 정확한 코드·테스트·재현 도구·보고서·선정 manifest를 반영한다. 채택한 한국어 추론 export 3파일을 `weights/paddle/korean_PP-OCRv5_mobile_rec/`에 반영하고 `weights/adopted_model.json` 및 필요한 다운로드/배포 경로도 일치시킨다.
4. 이 3개 추론 파일은 이미 Git 추적 대상이다. 현재 params는 약 13.34MB다. `.pdparams`/optimizer·원본·crop·대용량 로그는 제외한다. 신규로 다른 모델 파일을 채택하는 경우에만 정확한 allowlist와 용량 정책을 별도로 검토한다.
5. 최신 main의 다른 변경을 확인하고 사용자의 변경을 보존한다. 필요한 파일만 검토·stage하고 local 검증 후 커밋한다. 작업 브랜치에서 만든 커밋은 main에 정상 merge/fast-forward하고 force push나 hard reset을 사용하지 않는다.
6. 사용자가 직접 수행하려면 GitHub Desktop에서 커밋할 변경을 검토하고 main 반영·Push origin할 수 있게 준비한다. 에이전트가 수행하는 경우도 사용자 채택 후 요청 범위에 맞춰 수행한다. 불필요하게 양쪽에서 중복 커밋하지 않는다.
7. push 후 원격 main의 commit SHA 및 파일 상태를 확인해 보고한다. 원격 읽기 접근과 main 존재는 확인했지만 쓰기 권한·보호 브랜치 정책은 아직 검증하지 않았다. 직접 push가 제한돼 있으면 우회하지 않고 일반 PR 경로로 main 병합을 진행할지 보고한다.

기각 시 공용 weights와 main의 배포 모델은 유지한다. 후보·평가 이력은 보존하고 코드만 별도 채택할지 모델과 함께 기각할지는 사용자 결정으로 구분한다.

## 9. 예상 소요시간

아래는 아직 확정되지 않은 crop 수·고정 1 epoch 첫 후보를 전제로 한 공학적 추정이다. 달성 보장이 아니며 사용자 검토 대기·미해결 데이터 충돌·권한 문제·실패 재실행은 별도다.

| 작업 | 예상 | 비고 |
|---|---:|---|
| 정답·승인·그룹·crop 준비 및 학습 입력 계약 고정 | 45~90분 | 승인 이력 계승, 실제 pool 크기 확정 |
| 코드 수정·회귀 테스트 | 2~4시간 | 아래 학습과 병행, 입력 계약 변경은 동기화 |
| 누적 학습·내부 검증·export | 1~2시간 | 대략 2,000~4,000 optimizer crop, 1 epoch 시나리오 |
| 코드/후보 결합·해시·로딩·출력 검증 | 15~30분 | 둘 다 종료 후 |
| 1~5회 온라인 평가·채점 | 75~90분 | 세 묶음 병행 계획, 실패 재시도 별도 |
| 5개 보고서+종합 보고서·회귀 검토 | 30~60분 | 전체 사례·집계 확인 |
| 사용자 채택 후 main 반영·검증·커밋·push | 15~30분 | 사용자 결정 대기 제외, 권한/충돌 없을 때 |

코드와 학습을 단순 합산하지 않은 총 예상은 **보고서 제출까지 약 5~9시간**이다. 사용자 채택 후 반영은 별도 약 15~30분이다. 전수 수동 재검토가 필요한 정답/crop 충돌이 다수 발견되면 추가 시간이 필요하며 해당 건수와 사유를 먼저 보고한다.

학습 시간의 근거: 과거 같은 CPU 0–3/4스레드의 365 optimizer crop·25 validation crop·1 epoch는 46steps, 학습+검증 517.544초, 전체 프로세스 530.010초였다. 단순 규모 환산은 `8.63분 × (새 optimizer crop 수 / 365) × epoch 수`이며, 실제 crop 폭·문자 길이·검증 규모·메모리·epoch 0 검증·export 비용에 따라 달라진다. 2,000~4,000crop이면 이 단순 환산만 약 47~95분이므로 준비/검증 여유를 포함해 1~2시간으로 둔다. 실제 pool 확정과 초기 처리 속도 계측 후 추정을 갱신한다.

epoch를 추가하거나 모델별 대조 평가를 늘리는 것은 기본 시간 밖이다. 3 epoch로 확대하면 학습만 대략 3~6시간 규모가 될 수 있으므로 자동 확대하지 않는다. RAM 부족으로 전체 평가를 순차 실행하면 기본 계획보다 약 50~55분이 추가될 수 있다.

완료 조건은 (1) 승인한 학습 범위대로 실제 optimizer/검증 완료, (2) 고정 코드+후보로 1~5회 평가 시도와 실패 포함 전 결과 보존, (3) 6개 보고서 제출이다. 이후 사용자 채택 결정과 main 반영은 별도 관문이다.
