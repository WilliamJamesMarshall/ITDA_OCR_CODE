## 2. 미검출 점 인쇄 줄 복구

기본 OCR와 표제 확대 검출에도 날짜가 없을 때, 유일한 고신뢰 수평 기한 표제 왼쪽의 밝은 패널에서 픽셀 성분으로 납작한 줄을 찾는다. 검출용 이진 마스크는 줄 위치를 찾는 데만 사용하며, 실제 인식에는 원본 색상 crop의 가로 비율 보정 화면을 사용한다.

- 최대 2개 줄, 줄마다 가로 0.4·0.45배의 2개 화면, 배치 인식 1회(최대 4개 crop)로 제한한다.
- 두 화면에서 같은 원문 날짜 후보 집합이 나와야 한다. 줄 점수 ≥0.85, 정렬된 날짜 숫자 평균 ≥0.90, 최솟값 ≥0.70을 함께 요구한다.
- 숫자 치환으로만 성립하는 날짜는 채택하지 않는다. 두 줄 중 하나라도 불안정하면 블록 전체를 보류한다.
- 같은 모델의 화면 일치를 독립 투표나 보정된 확률로 해석하지 않는다. 점수를 가산하지 않고 지지 화면 중 낮은 점수를 유지한다.
- 날짜 역할·순서는 기존 표제 연결과 달력·명시된 제조일/기한 쌍 규칙으로 결정한다. 이 복구 기능 자체에서 YMD를 강제하지 않는다. 역할 근거가 없는 단일 모호 날짜의 DMY 기본값도 유지한다.
- 실패·경쟁 줄·여러 표제에서는 기존 전체 이미지/타일 복구를 유지한다. 원문 화면·위치·문자 점수·채택/보류 이유는 trace에 남긴다.

`003355`에서 `20.08.27`과 `21.05.26P`가 안정적으로 읽혔다. 끝의 P/F는 날짜 밖 문자이며 정답 날짜를 만들기 위해 지우거나 바꾸지 않는다. 두 줄에 대응하는 ‘부터/까지’와 같은 형식의 시작일 < 종료일 조건으로 YMD가 선택되어 **2021-05-26**을 출력한다. 이미지를 0.85배·1.15배로 바꿔 메모리에서 재검사한 경우에도 같은 결과와 조기 종료 경로를 확인했다. 이것은 동일 개발 사진의 크기 변화 검사이지 독립 표본 2장 추가가 아니다.

34장 전후 비교 중 이 사진의 처리시간은 **2.019 → 0.848초**였다. 직전에는 표제 확대 후 CLAHE와 복구 검출까지 실행하고도 날짜를 찾지 못했지만, 지금은 원본 → 표제 확대 → 줄 인식에서 종료한다.

## 3. 명확한 날짜 쌍의 불필요한 반복 제거

원인은 두 가지였다. 낮은 점수의 주변 설명 문장에서 ‘제조’가 발견되어 날짜 후보에 음수 문맥이 섞였고, 명확한 날짜에 낮은 점수의 이메일·중량 문장을 붙인 병합 관측이 별도의 약한 날짜 판독처럼 취급됐다.

주변 문맥은 OCR 점수 0.70 이상일 때만 사용한다. 날짜 자체의 인라인 근거는 이 조건으로 삭제하지 않는다. 기존의 제한된 가까운 날짜 쌍 정책이 성립한 경우에만, 모든 병합 날짜가 동일한 원문·값·원본 멤버의 독립 날짜로 설명되는지 검사한다. 독립 날짜 점수 ≥0.95, 두 값만 존재, 명시 제조일 충돌 없음 조건을 만족하면 병합 문장의 낮은 점수만으로 추가 OCR을 요구하지 않는다. 제3의 날짜, 새 날짜 조각, 명시된 역할 충돌은 이 종료 조건에서 제외한다.

`003714`는 날짜를 첫 패스에서 읽었어도 ROI 2회·CLAHE·복구 검출까지 수행하던 상태에서 **원본과 줄 재확인만 수행**하도록 바뀌었다. 최종 날짜 `2023-07-01`을 유지하면서 **7.702 → 2.495초**로 줄었다. 순서에 DMY 기본값을 사용했다는 `order_resolved=False`는 계속 보존한다.

34장 전체에서 CLAHE 호출은 11→9회, 복구 검출은 10→8회였다. **타일 호출은 각 위치 3회로 같았다. 타일 비용까지 해결했다고 보고하지 않는다.**

## 4. 시간 목표와 제출 계약

전후 실제 OCR 비교는 동일 입력 해시·동일 백엔드·실행 순서 교차로 수행했다. 두 방식이 공유한 초기화 3.731초는 아래 평균에서 분리했다.

| 34장 평균 | 변경 전 | 변경 후 | 변경 후 − 장당 목표 3초 |
|---|---:|---:|---:|
| OCR 백엔드 호출 시간 | 2.644초 | 2.472초 | −0.528초 |
| 이미지 로딩·전처리·판정 포함, 공유 초기화 제외 | 2.760초 | 2.579초 | −0.421초 |

이미지 처리 평균은 약 6.6% 감소했다. 이후 별도로 실행한 **기존 14장 제출 경로**는 다음과 같다.

- 전체 실행시간 **47.294초 / 14장 = 3.378초/장**. 작업 프로세스 시작/import·초기화·이미지 탐색/로딩·OCR·판정·CSV 저장을 포함한다. 부모의 초기 준비/라벨 로딩과 최종 평가 보고서 저장은 제외한다.
- OCR 백엔드 호출 시간 **2.942초/장**. 장당 3초보다 **0.058초 짧음**. 호출 중 복구 모델 지연 초기화가 포함되며 이미지 로딩·전처리·판정·로그/CSV 저장은 제외한다.
- 전체 시간은 3초보다 **0.378초/장 길어 내부 상대 시간 목표 미달**이다. OCR 시간만으로 결합 목표 달성을 선언하지 않는다.
- 상대 소프트 예산 `14×3=42초`를 넘겨도 종료하지 않고 전체 14장을 처리했다. 상태는 `internal_target_missed_within_hard_limit`다.
- 정확한 날짜 14/14, 제출 형식 14/14, 실행 오류·누락 0건. 완전 누락은 `NONE-NONE-NONE`, 부분 날짜는 원래 알려진 필드를 보존한다.
- 500장 실제 실행 여부와 500장 통과/실패는 미측정(null)이다. 1,500초 소프트 목표·2,400초 강제 종료·95% 정확도 목표는 변경하지 않았다.

직전 14장 실행 기록은 55.113초였지만 별도 시점의 단일 실행이므로 전체 차이를 코드 효과로 단정하지 않는다. 코드 전후 속도 비교의 근거는 위 34장 교차 실행이다.

## 5. 검증 범위와 남은 작업

`karpathy-guidelines`에 따라 전처리를 모든 이미지에 추가하지 않고 좁은 진입 조건과 반례 테스트를 붙였다. 새 15개 테스트에는 한 줄 실패 시 전체 보류, 정렬 문자 점수 부재, 숫자 치환 거부, 단일 모호 날짜의 DMY 유지, 여러 표제/세 줄 거부, 좌표 보존, 선택 근거 추적, 선택적 인식 실패 시 기존 복구, 병합 제조일 충돌·제3의 날짜를 포함했다. 전체 210개 테스트, Python 문법 검사, 공백 검사, 실행 전후 코드 해시와 입력 해시 확인을 완료했다.

**다음 작업은 있다.** 이번에 다룬 `003355` 복구와 `003714`의 불필요한 전체 재인식은 해결했지만, 전체 평균 3초/장 목표까지 완료한 것은 아니다.

1. 기존 개발 자료의 미해결/부분 날짜 사례(`003512`, `003560` 등)에서 전체 이미지·4개 타일이 실제 추가 근거를 제공하는지 분석하고, 영역에 근거한 제한적 재시도·종료 조건을 검증한다. 단순히 3초에서 끊거나 제조일을 소비기한으로 채워 넣지 않는다.
2. 다른 점 인쇄·납작한 글꼴 개발 표본에서도 줄 위치와 실제 문자 주석을 대조해 적용 범위와 오탐을 검증한다. 이번 한 사진과 크기 변화 검사만으로 범용 복구나 보완 학습 완료를 선언하지 않는다.

독립 500장 및 `테스트용데이터`는 계속 이번 세션의 다음 작업에서 제외한다.
