호대표, 이 사례들은 **OCR이 숫자만 읽게 하면 오판하기 쉽고, “한국 식품 소비기한 표기 문맥 + 날짜 형식 + 주변 문자”를 같이 판단하는 후처리 정책**이 필요합니다. 특히 `26.04.24 B 17:20`을 `2024-04-26`처럼 뒤집어 읽는 문제를 막는 것이 핵심입니다.

사진에 있는 표기는 전부 다음처럼 해석하는 게 맞습니다.

| 사진       | OCR 원문 예시              | 올바른 소비기한       | 날짜 외 정보                         |
| -------- | ---------------------- | -------------- | ------------------------------- |
| ABC 초코쿠키 | `26.04.24 B` / `17:20` | **2026-04-24** | `B` = 생산/라인 코드 추정, `17:20` = 시간 |
| 빼빼로 흰색   | `26.06.17 09:23 F2`    | **2026-06-17** | `09:23` 시간, `F2` 코드             |
| 빼빼로 빨강   | `26.05.30 06:18 F2`    | **2026-05-30** | 동일                              |
| ABC 초코쿠키 | `26.06.04 B` / `11:32` | **2026-06-04** | B 및 시간 제외                       |
| 보라색 제품   | `26.08.30 A` / `08:14` | **2026-08-30** | A 및 시간 제외                       |
| 음료       | `소비기한 27.01.02 B 까지`   | **2027-01-02** | B 제외                            |
| 냉동식품     | `소비기한: 26.02.24 까지`    | **2026-02-24** | 날짜만 존재                          |

즉 이 샘플군에서는 **`YY.MM.DD`가 기본 규칙**입니다.

---

# 1. 가장 중요한 정책

OCR 모델에게 최종적으로 다음 원칙을 적용하시면 됩니다.

> **한국 내수 식품에서 `소비기한`, `유통기한`, `까지` 등의 문맥과 함께 `NN.NN.NN`이 발견되면 기본적으로 `YY.MM.DD`로 해석한다.**

따라서

```text
26.04.24
```

는

```text
2026년 04월 24일
```

입니다.

다음처럼 해석하면 안 됩니다.

```text
2024년 04월 26일 ❌
2026년 24월 04일 ❌
```

---

# 2. OCR 전체 처리 구조

단순하게는 다음 5단계가 가장 안정적입니다.

```text
이미지
  ↓
① 소비기한 영역 탐지
  ↓
② OCR
  ↓
③ 문자열 정규화
  ↓
④ 날짜 후보 추출
  ↓
⑤ 문맥 + 날짜 유효성 기반 최종 판정
```

즉 **OCR 자체가 날짜를 이해하게 만들기보다, OCR은 문자를 읽고 뒤에서 Date Parser가 소비기한을 판정**하는 구조를 권합니다.

---

# 3. 1단계: 소비기한 영역 탐지

전체 포장지를 OCR하면 잡음이 너무 많습니다.

예를 들어 사진에는

```text
8801062893546
26.06.04 B
11:32
```

가 같이 있습니다.

OCR만 보면 바코드 숫자까지 날짜 후보가 될 수 있습니다.

따라서 우선 다음 키워드를 탐색합니다.

```text
소비기한
유통기한
품질유지기한
까지
BEST BEFORE
EXP
EXPIRY
```

그리고 키워드 주변 일정 범위를 **날짜 ROI(region of interest)** 로 지정하는 방식이 좋습니다.

예:

```text
소비기한:     26.02.24      까지
              └─────────┘
               DATE ROI
```

다만 첫 번째 사진처럼 앞쪽에 `소비기한`이라는 단어가 안 보이고 뒤에 `까지`만 존재할 수도 있으므로,

```text
소비기한
또는
까지
```

중 하나만 검출되어도 후보로 인정합니다.

---

# 4. 2단계: 날짜 후보 정규식

우선 아래 패턴을 날짜 후보로 잡습니다.

```regex
\b\d{2,4}[.\-/]\d{1,2}[.\-/]\d{1,2}\b
```

예:

```text
26.04.24
26-04-24
26/04/24
2026.04.24
2026-04-24
```

모두 날짜 후보입니다.

조금 더 실전적으로는 공백도 허용합니다.

```text
26 . 04 . 24
26. 04. 24
```

OCR이 흔히 점 주변에 공백을 집어넣기 때문입니다.

---

# 5. 가장 중요한 날짜 형식 판정 정책

한국 내수 식품이면 우선순위를 다음과 같이 두는 것을 권합니다.

### Priority 1 — YYYY.MM.DD

```text
2026.04.24
```

처럼 첫 숫자가 4자리라면 사실상 확정입니다.

```text
YYYY-MM-DD
```

로 변환합니다.

---

### Priority 2 — YY.MM.DD

```text
26.04.24
```

처럼 모두 2자리라면 한국 내수상품에서는 기본적으로

```text
YY.MM.DD
```

로 해석합니다.

따라서:

```text
26.04.24 → 2026-04-24
26.06.17 → 2026-06-17
27.01.02 → 2027-01-02
```

---

# 6. DD.MM.YY 오판 방지 규칙

이게 상당히 중요합니다.

예를 들어

```text
26.04.24
```

는 숫자만 보면

```text
YY.MM.DD = 2026-04-24
DD.MM.YY = 2024-04-26
```

둘 다 달력상 유효합니다.

따라서 **날짜 유효성 검사만으로는 구분이 불가능합니다.**

반드시 국가/제품 문맥 정책을 둬야 합니다.

```pseudo
if country == KR
   and product_type == food
   and language_context == Korean:
       ambiguous_XX_XX_XX => YY.MM.DD
```

즉 한국 제품이라는 metadata가 있으면 그것을 적극 활용하는 것이 좋습니다.

---

# 7. 월/일 유효성 검증

날짜 후보를 인식한 다음 반드시 달력 검증을 합니다.

예:

```text
26.14.04
```

를

```text
2026-14-04
```

로 만들면 안 됩니다.

월은:

```text
1 ≤ MM ≤ 12
```

일은:

```text
1 ≤ DD ≤ 해당 월의 마지막 날
```

이어야 합니다.

예:

```text
26.02.29
```

2026년은 윤년이 아니므로 invalid입니다.

이 경우에는 OCR 오인식 가능성을 판단해야 합니다.

예:

```text
26.02.28
26.02.20
26.02.23
```

등을 후보로 재검토하되 **임의 보정해서 확정하면 안 됩니다.**

---

# 8. A / B / F2 같은 문자를 날짜에서 제외

사진에서 매우 중요한 패턴입니다.

```text
26.04.24 B
26.08.30 A
27.01.02 B
26.06.17 09:23 F2
```

여기서

```text
A
B
F2
```

는 소비기한 일부가 아닙니다.

따라서 정책을:

```text
YY.MM.DD 이후에 등장하는
1~3자리 영문/영숫자 코드는 생산공장·라인·LOT 코드 후보로 처리
```

로 설정하면 됩니다.

예:

```text
26.04.24 B

date = 2026-04-24
lot_code = B
```

또는

```text
26.06.17 09:23 F2

date = 2026-06-17
time = 09:23
lot_code = F2
```

---

# 9. 시간과 날짜를 분리

사진처럼 상당수 제조사가

```text
26.06.17 09:23 F2
```

처럼 찍습니다.

따라서 다음 패턴은 명확하게 **시간**으로 분류합니다.

```regex
([01]?\d|2[0-3]):[0-5]\d
```

즉

```text
17:20
09:23
06:18
11:32
08:14
```

는 소비기한 날짜에 절대로 포함하지 않습니다.

결과는 다음과 같습니다.

```json
{
  "expiration_date": "2026-06-17",
  "production_time": "09:23",
  "lot_code": "F2"
}
```

실제로는 `production_time`인지 `printing_time`인지 확정할 수 없기 때문에 DB 필드 이름은 오히려

```text
printed_time
```

또는

```text
auxiliary_time
```

정도로 두는 편이 안전합니다.

---

# 10. OCR 오인식 교정 규칙

도트 프린터 방식이라 OCR 오류가 상당히 많이 발생할 수 있습니다.

특히:

```text
0 ↔ O
1 ↔ I ↔ l
2 ↔ Z
5 ↔ S
6 ↔ G
8 ↔ B
```

가 자주 생깁니다.

다만 **날짜 후보 영역에서만** 보정해야 합니다.

예:

```text
26.O6.17
```

→ 날짜 영역이므로

```text
26.06.17
```

로 보정 가능.

그러나 상품명이나 LOT 코드에서는

```text
F2 → F2
```

를 유지해야 합니다.

전역 치환을 해버리면

```text
B → 8
F2 → F2
```

같은 이상한 오류가 생깁니다.

그래서:

```pseudo
if token classified as DATE_CANDIDATE:
    O -> 0
    I/l -> 1
    Z -> 2
    S -> 5
else:
    no forced correction
```

로 하시면 됩니다.

---

# 11. 점 `.` 인식 오류도 처리

도트마킹 특성상 다음처럼 읽힐 수 있습니다.

```text
26.06.17
26 06 17
26:06:17
26·06·17
26-06-17
```

따라서 날짜 후보 영역에서는 separator를 어느 정도 통합해도 좋습니다.

```text
.
-
/
·
공백
```

→

```text
.
```

다만 `:`는 주의해야 합니다.

```text
09:23
```

이라는 시간이 존재하기 때문입니다.

그래서 **세 묶음 숫자인 경우만 날짜 separator 후보**로 보는 게 좋습니다.

---

# 12. `까지`의 중요도를 높게 두기

한국 포장식품에서

```text
26.04.24 B
17:20          까지
```

와 같은 구조가 존재합니다.

따라서 OCR 결과에서 날짜와 `까지` 사이 거리가 가까울수록 expiration confidence를 높입니다.

예를 들어 점수화하면:

| 조건           | Score |
| ------------ | ----: |
| `소비기한` 바로 뒤  |   +50 |
| `까지` 바로 앞    |   +40 |
| YY.MM.DD 형식  |   +30 |
| 실제 달력상 유효    |   +30 |
| 현재 기준 미래 날짜  |   +10 |
| HH:MM 형태     |  -100 |
| 8~14자리 연속 숫자 |  -100 |
| barcode 인접   |   -30 |

예:

```text
8801062879090
26.04.24 B
17:20
           까지
```

라면

```text
26.04.24
```

가 압도적으로 높은 점수를 얻게 됩니다.

---

# 13. 현재 날짜를 활용하되 절대조건으로 만들면 안 됨

현재가 2026년이라고 해서 무조건 2026년 이후 숫자만 소비기한으로 인정하면 안 됩니다.

이미 지난 상품을 촬영할 수도 있기 때문입니다.

다만 후보가 여러 개라면 보조점수로 사용할 수 있습니다.

예:

```text
24.04.26
26.04.24
```

둘 다 탐지된 경우,

제품 판매·촬영 시점이 2026년이고 소비기한 문맥상 2026년 날짜가 자연스럽다면 후자의 점수를 조금 높일 수 있습니다.

하지만:

```pseudo
expiration_date < today
=> reject
```

는 쓰시면 안 됩니다.

대신:

```pseudo
expiration_date < today
=> confidence - small_penalty
```

정도가 적절합니다.

---

# 14. 바코드 제거 규칙

사진들에서 날짜 바로 위에 EAN-13 바코드가 있습니다.

예:

```text
8801062879090
```

따라서

```regex
^\d{8,14}$
```

형태의 연속 숫자는 날짜 후보에서 제외합니다.

특히

```text
8801062 879090
```

같이 OCR이 공백을 끼워 읽을 수도 있으므로 barcode detector 결과를 함께 사용하는 것이 가장 좋습니다.

---

# 15. 소비기한과 제조일자 구분

실제 서비스에서는 이것도 반드시 필요합니다.

다음 키워드를 별도 클래스화하십시오.

```text
소비기한
유통기한
제조일
제조일자
생산일
포장일
품질유지기한
```

예:

```text
제조일자 26.04.24
소비기한 27.04.24
```

가 있다면 두 날짜 중 아무거나 반환하면 안 됩니다.

출력 구조를 아예:

```json
{
  "manufactured_date": "2026-04-24",
  "expiration_date": "2027-04-24"
}
```

처럼 나누는 것이 좋습니다.

---

# 16. 가장 추천하는 Confidence 정책

최종 결과를 무조건 하나 찍는 것보다 3단계로 나누는 것이 좋습니다.

### HIGH

다음처럼 명확한 경우:

```text
소비기한 27.01.02 B 까지
```

→

```text
2027-01-02
confidence: 0.99
```

---

### MEDIUM

```text
26.04.24 B
17:20
```

옆에 `까지`만 존재하는 경우.

→

```text
2026-04-24
confidence: 0.90
```

---

### LOW / REVIEW

예:

```text
04.05.06
```

인데

* 한국어 문맥 없음
* 소비기한 문구 없음
* 수입제품
* 국가정보 없음

이라면

```text
2004-05-06
2006-05-04
2006-04-05
```

여러 해석이 가능합니다.

이 경우 모델이 찍지 말고:

```json
{
  "expiration_date": null,
  "status": "REVIEW_REQUIRED",
  "candidates": [...]
}
```

로 보내는 게 훨씬 안전합니다.

---

# 17. 해외 제품에는 같은 규칙을 적용하면 안 됩니다

이 정책은 매우 중요합니다.

한국 제품:

```text
26.04.24
→ YY.MM.DD
→ 2026-04-24
```

라고 해도,

유럽 제품에서

```text
26.04.24
```

는

```text
DD.MM.YY
→ 2024-04-26
```

일 가능성이 있습니다.

미국 제품이라면 또

```text
MM.DD.YY
```

가 쓰일 수 있습니다.

따라서 최상단에:

```text
COUNTRY / MARKET CLASSIFIER
```

를 두는 것이 좋습니다.

```pseudo
KR → YMD 우선
JP → YMD 우선
US → MDY 우선
EU/UK 일부 → DMY 우선
Unknown → ambiguous 처리
```

---

# 18. 실제 구현용 정책을 압축하면

개발자에게는 아래 정도로 전달하시면 됩니다.

```text
[소비기한 OCR Parsing Policy]

1. '소비기한', '유통기한', '까지' 주변의 OCR text를 우선 분석한다.

2. 날짜 후보:
   YYYY.MM.DD
   YY.MM.DD
   YYYY-MM-DD
   YY-MM-DD
   YYYY/MM/DD
   YY/MM/DD

3. 한국 내수제품이며 2자리 숫자 3개 형식인 경우
   기본 format = YY.MM.DD.

4. YY는 20YY로 변환한다.
   예: 26.04.24 → 2026-04-24.

5. 뒤따르는 A, B, F1, F2 등의 영문/영숫자 값은
   LOT/라인 코드로 간주하고 날짜에서 제외한다.

6. HH:MM 형식은 시간으로 분류하며 날짜에서 제외한다.

7. 월은 01~12, 일은 해당 월의 유효한 날짜인지 검증한다.

8. 날짜 ROI 안에서만 OCR 문자 오인식을 교정한다.
   O→0, I/l→1 등.

9. 8~14자리 연속 숫자는 barcode 후보로 날짜에서 제외한다.

10. '소비기한'과 가장 가까운 날짜 또는
    '까지' 바로 앞 날짜에 높은 confidence를 부여한다.

11. '제조일자'와 '소비기한'은 별개의 entity로 분류한다.

12. 형식이 모호하거나 국가가 불분명하면 임의 확정하지 않고
    REVIEW_REQUIRED로 반환한다.
```

그리고 머신러닝 모델의 목표 출력도 그냥 문자열 하나보다 다음과 같이 만드는 것을 추천합니다.

```json
{
  "raw_text": "26.06.17 09:23 F2",
  "expiration_date": "2026-06-17",
  "date_format": "YY.MM.DD",
  "auxiliary_time": "09:23",
  "lot_code": "F2",
  "market": "KR",
  "confidence": 0.98,
  "reason": [
    "Korean food packaging",
    "YY.MM.DD pattern",
    "valid calendar date",
    "near expiry label"
  ]
}
```

핵심은 **“OCR → 바로 날짜”가 아니라 `OCR → 날짜 후보 추출 → 한국 식품 문맥 판정 → 달력 검증 → 소비기한 entity 결정`**로 분리하는 것입니다. 이렇게 해야 사진처럼 `B`, `A`, `F2`, 시각, 바코드가 뒤섞여 있어도 안정적으로 처리할 수 있습니다.
